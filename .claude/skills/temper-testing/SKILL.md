# Testing in Temper

Tests live in the same module as the code, as `test` blocks. A module
with any `test` block is a test module; each backend extracts them into
its own framework (mocha, pytest, cargo test, MSTest, JUnit).

```temper
test("greeting") {
  assert(greetingFor("x") == "Hello, x!");            // default message:
  assert(c.bump() == 2) { "custom message ${c.count}" } // expected c.bump() == (2) not (1)
}
```

- `assert` is **soft**: the test keeps running and every failed message
  is reported, joined with `, `. `test.assertHard(cond) { msg }` stops.
- To use `assert` in a helper, give the helper a parameter named `test`
  or typed `Test` (`let { Test } = import("std/testing")`) and pass it:

  ```temper
  test("cases") { test => runCases(test); }
  let runCases(test: Test): Void { assert(1 == 1); }
  ```

- Output per backend: `Test failed (js): <name> - <messages>` then
  `Tests passed: N of M` and `Test failed`. No `Tests passed:` line at all
  means the run never reached the tests.

## Test helper names must be unique across the whole library

The Elixir backend puts every class of every module into one namespace
(`Temper.Dave.Run`), test helpers included; the last definition wins. Two
test files that each declare `class Run(...)` with different constructors
pass on interp, js, py, lua, rust and csharp and fail on elixir with
`function Temper.Dave.Run.new/3 is undefined ... Did you mean: new/2`,
reported as `0 of N (N not run)`. Prefix helper classes and functions with
the module (`ComposeRun`, `AgentRun`, `agentRoles`); see
`src/agent/agent_test.temper`.

## Test files do not re-import std names

The files of a module share one scope, so a test file sees the library
files' `import("std/...")` bindings. Do not import them again in the test
file: the js backend then drops the std *function* from the extracted
`test/<module>.js` and the ReferenceError comes back as a bubble
(`probes/js-test-std-import`, upstream #630). Keep tests in the same module as the code
(`src/<module>/<module>_test.temper`) so internals need no `export`.

## The compile-time folding trap

The frontend folds calls whose inputs are all literals. A test that
compares `hash("a", "b")` to a literal may be evaluated by the compiler's
interpreter and the backend never runs `hash` at all; the test proves
nothing about the translation. growthbook's harness comment:

> Every check runs inside a function that takes the `test`. The Temper
> frontend folds calls whose inputs are all known at compile time, which
> would test the compiler's interpreter instead of the generated code.

So put real checks in a function called from the test block, and feed
inputs through something the frontend cannot see through (a list it
iterates, a parsed string).

## Data-driven tests

Temper has no file I/O. Fixture data becomes a Temper source file with
string literals, generated by a script in `scripts/` (growthbook:
`gen-cases.py` writes `src/tests/cases.temper`). Then one `test` per
category iterates the cases, tallies, and reports one assertion whose
message names every failing case and reason: `"<cat>: 12 of 13 passed || <case> :: got X want Y"`.
That pattern is what `scripts/matrix.sh` reads.

Expected values that must match a reference implementation (Node's
`JSON.stringify`, Python's `json`, an API's documented output) are
recorded from the reference by a script, not typed by hand.

## Running

```bash
bin/temper test -b interp            # seconds; semantic reference
bin/temper test -b js                # first real backend
scripts/matrix.sh                    # every backend that runs here -> MATRIX.md
scripts/matrix.sh py rust            # a subset
```

One backend per process; they share `temper.out/`. Logs land in
`build/matrix/<backend>.log`.

## When backends disagree

That is the finding. Steps:

1. Reduce to a probe: a minimal library in the scratchpad (or
   `probes/<slug>/` if it will matter again) with `src/config.temper.md`
   and one file. `scripts/probe.sh <dir> interp <backend> --show`.
2. Read the generated code for the construct. Say which side is wrong
   relative to Temper's semantics (interp).
3. Record: `observation` node, the probe output in the commit message,
   and if the gap stays open, a row note in MATRIX.md and a `TODO` in the
   code naming the backend and the construct. Never paper over it with a
   fallback that makes the test green.

## Reading a crash

- A Python traceback or a Rust panic in `Test failed (py): name - ...`:
  the Temper frontend accepted the code; the translation or the std
  implementation on that backend broke. Line numbers point into
  `temper.out/<backend>/dave/tests/`; the `.map` files (js) map back.
- `Build failed` lines before the test run: a frontend error. The tests
  may still execute on stale or partial output; fix the error first and
  ignore the test numbers.
- `RuntimeError37()` in py / bare `fail` in interp is an unhandled Bubble.
  Bubble carries no message; find which `orelse` or `as` is missing.
